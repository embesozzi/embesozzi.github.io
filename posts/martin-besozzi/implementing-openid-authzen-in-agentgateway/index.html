Implementing OpenID AuthZEN in Agent Gateway: MCP Tool Authorization

15 Sep, 2026
|

A companion piece to Mastering Secure APIs and AI Agents with Zero Trust and Fine-Grained Authorization Based on OpenID AuthZEN, this article walks through a concrete, runnable implementation.

The example shows how to enforce OpenID AuthZEN authorization decisions for MCP tool calls using Agent Gateway as the Policy Enforcement Point (PEP) and Keycloak as both the OpenID Provider and Policy Decision Point (PDP).

The implementation is available in agentgateway/agentgateway#3478, which adds an examples/mcp-authzen example to the project.

The problem

Traditional authorization approaches struggle with three fundamental problems:

  1. Poor interoperability, leading to vendor lock-in. Each authorization system speaks its own language, so switching PDPs or integrating across platforms means significant rework.
  2. Growing complexity that doesn’t scale. As systems expand, authorization rules multiply. Logic embedded in application code becomes unmaintainable and inconsistent across services.
  3. Tight coupling of authorization logic in application code. When policies live inside application code, every policy change requires a development cycle, testing, and a deployment, a recipe for security drift and technical debt.

Why AuthZEN?

If you’re new to OpenID AuthZEN, the simplest way to think about it is:

AuthZEN standardizes how an application asks an external authorization service whether an operation is allowed.

OpenID AuthZEN addresses this by standardizing a common interface between two components:

  • Policy Enforcement Point (PEP) the component receiving the request and enforcing the authorization decision.
  • Policy Decision Point (PDP) the component that evaluates the request against authorization policy and returns the decision.

In this implementation, Agent Gateway is the PEP and Keycloak is the PDP.

Instead of embedding authorization logic in every application, you externalize the decision to a dedicated policy engine. Agent Gateway does not need to understand how the authorization policy is implemented. It only needs to construct an AuthZEN authorization request and enforce the resulting decision.

What does an AuthZEN request look like?

AuthZEN defines a standard request model based on four main concepts:

{
  "subject": { "type": "user", "id": "alice", "properties": {}},
  "resource": {"type": "tool", "id": "approve_payment", "properties": {}},
  "action": {"name": "tools/call", "properties": {}},
  "context": {}
}

In simple terms:

  • subject: who is requesting the operation.
  • resource: what the subject wants to access.
  • action: what operation they want to perform.
  • context: additional information that may influence the decision.

The PDP evaluates that request against its policies and replies with a Decision Response: {"decision": true} or {"decision": false}. The PEP does not need to know whether the PDP uses roles, attributes, relationships, or another authorization model internally. That policy logic stays outside the application enforcing the request.

Core benefits

  • Interoperability: connect any AuthZEN-compliant PDP without changing the authorization interface in the enforcing application.
  • Decoupled authorization: policy decisions are separated from enforcement logic.
  • Flexibility: the same interface can support different authorization models, including ReBAC, PBAC, and ABAC.
  • Policy independence: the PEP does not need to know how authorization policies are implemented.
  • Dynamic evaluation: decisions can use runtime context rather than relying only on permissions established when a token was issued.

Why is this useful for MCP?

MCP introduces a dynamic tool invocation model. An agent can discover tools and invoke them at runtime, so authentication alone does not answer an important question:

Is this caller allowed to invoke this particular tool right now?

AuthZEN fills that gap as a dynamic, externalized authorization layer alongside OAuth. For protected tool calls, the authorization decision is evaluated at request time against the current policy rather than relying solely on permissions established when the session was created.

This article stays focused on MCP, but nothing about the PEP/PDP contract is MCP-specific. The same evaluation request shape (subject, resource, action, context) works for a plain REST API, which is the point: one standard, one PDP integration, enforced consistently across APIs, MCP servers, and whatever else sits in the request path. The prior article covers the API and MCP Apps cases in more depth.

The same architecture can later be extended to fine-grained authorization, where the decision also depends on the arguments of the tool call, such as the payment amount or destination account.

Architecture

The example has four components:

ComponentRole
MCP clientCalls the Payments MCP tools
AgentgatewayMCP gateway and AuthZEN Policy Enforcement Point
KeycloakOpenID Provider and AuthZEN Policy Decision Point
Payments MCP serverBackend exposing the payment tools

Agent Gateway sits between the MCP client and the Payments MCP server. For a tools/call request, it validates the caller’s token, constructs an AuthZEN evaluation request, sends it to Keycloak, and enforces the resulting decision.

Keycloak plays two roles in this example:

1 It issues the OAuth access token used by the MCP client.
2.It evaluates the AuthZEN authorization request as the PDP.

The resulting flow is:

sequenceDiagram participant Client participant GW as Agent Gateway <br> AuthZEN PEP participant KC as Keycloak <br> AuthZEN PDP participant MCP as Payments MCP server Client->>GW: tools/call + Bearer JWT (mcp-client) GW->>GW: jwtAuth validates the token GW->>KC: RFC 8693 token exchange<br/>(subject=inbound JWT, audience=mcp_proxy) KC-->>GW: token minted for mcp_proxy GW->>KC: POST /access/v1/evaluation<br/><br/>Authorization: Bearer <mcp_proxy token> KC-->>GW: 200 {"decision": true|false} alt decision == true GW->>MCP: Forward tools/call MCP-->>GW: Result GW-->>Client: Result else decision == false GW-->>Client: 403 Forbidden end

The token exchange step is Keycloak-specific plumbing. It authenticates the gateway to Keycloak’s protected AuthZEN evaluation endpoint. It is not part of the AuthZEN protocol itself.

A different AuthZEN-compliant PDP could use a different authentication mechanism without changing the basic PEP/PDP model.

The Agentgateway config, block by block

Everything below comes from the working example in agentgateway/agentgateway#3478, which adds examples/mcp-authzen to the project. This is the authorization-relevant part of the example’s config.yaml, walked through step by step.

1. Validate the inbound session token

mcp:
  port: 3000
  policies:
    jwtAuth:
      issuer: http://localhost:7080/realms/mcp
      audiences: [mcp_proxy]
      jwks:
        url: http://localhost:7080/realms/mcp/protocol/openid-connect/certs

Standard JWT validation against Keycloak’s mcp realm: this validates the caller’s token and establishes the identity and claims used by the authorization flow.

2. Only invoke the PDP for tool calls

    extAuthz:
      conditional:
      - condition: has(mcp.tool)
        host: localhost:7080

mcp.tool is only populated on a tools/call request. initialize, tools/list, and other MCP requests never invoke the PDP. The gate is a single CEL expression, so there’s no additional authorization overhead for MCP operations that don’t require an authorization decision.

3. Authenticate the gateway to the AuthZEN endpoint (Keycloak-specific)

        policies:
          backendAuth:
            oauthTokenExchange:
              host: localhost:7080
              path: /realms/mcp/protocol/openid-connect/token
              subjectToken:
                source:
                  header:
                    name: x-token-exchange-subject
              audiences: [mcp_proxy]
              clientAuth:
                clientId: mcp_proxy
                clientSecret: mcp-proxy-secret
                method: clientSecretBasic

This is the RFC 8693 token exchange from the sequence diagram: the gateway trades the caller’s validated token for one issued to mcp_proxy, which is what’s actually authorized to call Keycloak’s AuthZEN evaluation endpoint. A PDP that exposes its evaluation endpoint differently wouldn’t need this block.

4. Build the AuthZEN evaluation request

        protocol:
          http:
            path: '"/realms/mcp/authzen/access/v1/evaluation"'
            addRequestHeaders:
              content-type: '"application/json"'
              :method: '"POST"'
              x-token-exchange-subject: jwt.rawToken.unredacted()
            body: |
              {
                "subject": {"type": "user", "id": jwt.sub},
                "resource": {"type": "tool", "id": mcp.tool.name},
                "action": {"name": "tools/call"},
                "context": {"agent": jwt.azp}
              }
            metadata:
              decision: json(response.body).decision

This is where the MCP request becomes an AuthZEN authorization request:

AuthZEN fieldSourceExample
subject.idjwt.subalice
resource.idmcp.tool.nameapprove_payment
action.namefixed valuetools/call
context.agentjwt.azpmcp-client

This mapping follows a general model of AuthZEN CoAZ MCP binding.

In this example, authorization is intentionally tool-level to keep the implementation simple. The same approach can be extended to fine-grained authorization (FGA) by including tool arguments or other context in the authorization request.

5. Enforce the decision

    authorization:
      rules:
      - require: '!has(mcp.tool) || extauthz.decision == true'

One line: if this isn’t a tool call, let it through; if it is, require decision == true. Everything upstream exists to make this expression answerable.

Running it

The example can be run locally from the Agent Gateway repository.

# Start Keycloak, bootstrap the mcp realm, start the Payments MCP server
docker compose -f examples/mcp-authzen/docker-compose.yaml up -d

# Start agentgateway with the example config
cargo run -- -f examples/mcp-authzen/config.yaml

The keycloak/bootstrap-authzen.sh script provisions the mcp realm, including the users, roles, OAuth clients, and authorization resources and policies used by the example.

How the Keycloak policies work

The example uses Keycloak’s authorization model to map the MCP tools to authorization resources and scopes. Policies then associate the payments_user, payments_manager, and payments_admin roles with the resources and scopes they are allowed to access. For example, approve_payment is protected so that managers and admins can invoke it, while payments_user cannot.

When Agent Gateway sends an AuthZEN evaluation request, Keycloak evaluates the request against these policies using the subject, resource, and action from the request. This is why Alice receives {"decision": false} when calling approve_payment, while Bob receives {"decision": true}.

The mock Payments MCP server exposes five tools (list_accounts, get_account, create_payment, approve_payment, cancel_payment), and access varies by role:

Seeing it work

This example includes cli-tests.sh which drives an MCP tool call end to end. It authenticates a user, establishes an MCP session, and invokes the requested tool.

Alice (payments_user)

Alice can list and create a payment, but she cannot approve one:

./cli-tests.sh alice list_accounts      # 200 - allowed
./cli-tests.sh alice create_payment     # 200 - allowed, creates pay-1
./cli-tests.sh alice approve_payment    # 403 - denied

Alice can create a payment because that’s within her role. approve_payment requires payments_manager, which she doesn’t hold, so agentgateway sends Keycloak this evaluation request for the approve_payment attempt:

{
  "subject": {"type": "user", "id": "alice"},
  "resource": {"type": "tool", "id": "approve_payment"},
  "action": {"name": "tools/call"},
  "context": {"agent": "mcp-client"}
}

and gets back {"decision": false}. Agentgateway’s authorization rule rejects the call before it ever reaches the Payments MCP server.

Bob (payments_user)

Bob has the required has everything alice has, plus approval authority.

./cli-tests.sh bob approve_payment      # 200 - allowed, approves pay-1

The evaluation request agentgateway sends is identical in shape, just with bob’s subject:

{
  "subject": {"type": "user", "id": "bob"},
  "resource": {"type": "tool", "id": "approve_payment"},
  "action": {"name": "tools/call"},
  "context": {"agent": "mcp-client"}
}

This time Keycloak returns {"decision": true}, and the call goes through. Same code path, same config, same extAuthz call; the only thing that changed is the AuthZEN decision Keycloak returned.

A few things worth noticing in that pair of runs:

  • The 403 for alice never reaches the payments server. It’s rejected by agentgateway’s authorization rule directly from Keycloak’s decision: false, before the request is proxied anywhere.
  • Every tool call, allowed or denied, goes through the identical authorization path. Nothing tool-specific is hardcoded in Agent Gateway’s config; the only thing that varies is the PDP’s answer.
  • initialize and tools/list always succeed regardless of role, since extAuthz only fires when mcp.tool is set, i.e., only on tools/call.

Where this goes next: from CGA to FGA

What’s implemented here is coarse-grained authorization (CGA) at the tool level: is this subject allowed to call this tool? This keeps the example focused on the core PEP/PDP integration.

The same architecture can also support fine-grained authorization (FGA), where the decision depends on the specific arguments of the call, such as the payment amount, account, or recipient, rather than just the tool name. I’ll cover these extensions in future articles and workshops as the OpenID AuthZEN Working Group’s formal MCP binding draft matures.

Beyond FGA, authorization can also consider the user’s intent and the agent’s planned actions, rather than evaluating each tool call in isolation. I explore this model in Intent Agent Native Authorization, where authorization is tied to the intent behind an agentic workflow and can be combined with explicit user approval for sensitive actions.

Conclusion

This example demonstrates how OpenID AuthZEN can be used to externalize authorization for MCP tool calls.

Agent Gateway acts as the Policy Enforcement Point, Keycloak acts as the Policy Decision Point, and AuthZEN provides the standardized interface between them.

The current implementation performs coarse-grained authorization at the tool level:

Can this subject call this MCP tool?

It deliberately does not yet make decisions based on tool arguments.

That provides a simple foundation for extending the same architecture toward fine-grained authorization, where the PDP can evaluate the specific operation being requested.

The key idea is simple:

Agent Gateway enforces the decision. Keycloak makes the decision. AuthZEN connects them.
